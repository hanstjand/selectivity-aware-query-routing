\section{Experimental Setup}
\label{sec:setup}

\textbf{Data and workload.} We use the \code{laion-small-clip} collection of Qdrant's public filtered-ANN
benchmark~\cite{qdrant-datasets}: 100{,}000 CLIP image embeddings from LAION-400M with 512 dimensions, stored as
float32 with cosine distance (Table~\ref{tab:config}). The filter attribute is the payload field \code{similarity}, a
CLIP image--text score with 97{,}798 distinct values. The benchmark's own filters cover only about 3\%--99.5\%
selectivity, so we build new ones: for 300 of its test query vectors (sampled with a fixed seed) and each target
selectivity $\sel\in\{0.1,0.5,1,2,5,10,25,50,90\}\%$, a closed range covering $\mathrm{round}(\sel N)$ consecutive
attribute values is placed at a random offset, giving 2{,}700 configurations with $k=10$. Exact ground truth is
computed in NumPy with Eq.~\eqref{eq:cos}. As a check, we reproduce the benchmark's own neighbor lists under its
original filters: 297 of 300 match exactly, and the other three differ only between duplicate images at identical
distances.

\textbf{Database.} Vectors are loaded with binary \code{COPY} and stored inline, followed by a B-tree on
\code{similarity}, an HNSW index with pgvector's default build parameters, and one \code{ANALYZE}. Planner cost
constants are untouched, so B3 reflects the default planner, and every query is planned with its actual range
bounds. The HNSW query settings are fixed in advance; only $T$ is calibrated. A plain \code{EXPLAIN} of every
configuration--method pair (11{,}610 plans) confirmed that B1 never uses HNSW and every B2 plan is an HNSW scan, and B1
returns the exact ground truth except for two numerical near-ties.

\textbf{Protocol.} One client issues queries sequentially to PostgreSQL in Docker on the same machine. Tables and
indexes fit in the 2\,GB buffer pool and are prewarmed before each phase. After one untimed warm-up pass, five timed
passes run over all configuration--method pairs in a fresh random order, so drift affects all methods equally. The
calibration phase (37{,}800 timed executions) took 5.0\,min and the held-out phase (20{,}250) 2.5\,min, with no
failed execution. Latency is measured in the client from submission to the last fetched row, so it includes the round
trip and, for P1, the routing overhead.

\subsection{Evaluation Metrics}
\label{sec:metrics}
The latency $\lambda_m(c)$ of method $m$ on configuration $c$ is the median of the five timed runs; we report its p50,
p95 and mean over configurations. Recall@10 is the identifier overlap with the exact answer,
$r_m(c)=|R_m(c)\cap G_k(c)|\,/\,\min(k,|E(c)|)$, and a query is \emph{complete} if it returns $\min(k,|E(c)|)$ rows.
The quality targets are mean Recall@10 $\ge0.95$ and $\ge99\%$ complete queries. The estimation error is
$(\Mhat-|E|)/|E|$. The \emph{Oracle} takes, per configuration, the faster of B1 and B2-iter in hindsight, without
overhead or quality requirement; it is a latency floor, not a deployable method. P1's captured gain for a statistic
$S$ is
\begin{equation}
\Gamma_S=\bigl(S(\text{best})-S(\text{P1})\bigr)\,/\,\bigl(S(\text{best})-S(\text{Oracle})\bigr),
\label{eq:gain}
\end{equation}
where ``best'' is the fastest baseline meeting both quality targets on the same set of configurations.
